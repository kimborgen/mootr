# mootr design

Status: draft, 2026-10-10. This file is the how of the system.

## Decisions

| Topic | Decision | Why |
| --- | --- | --- |
| Language | TypeScript on Node 24, run directly (type stripping), no build step | One language for daemon, CLI, MCP shim, hooks, and web UI. `node:sqlite` is built in. |
| Terminal layer | Own tmux server on a dedicated socket (`tmux -L stam`); borrow ideas and code from herdr (Apache-2.0) where useful | tmux gives persistence and human attach for free. herdr lacks web view, mailbox, and structured control. |
| Control | Structured harness channels first: hooks, Claude Code channels, OpenCode server API, Codex app-server. Keystrokes only at moments nobody types, such as answering a launch dialog | Spikes: typed injection merged a mail into a half-typed draft in both harnesses tested. |
| State | From hooks and harness events, not screen scraping | Exact, and the same events drive mail delivery. |
| Storage | SQLite on the hub; attachments as files next to it | One file, no server. |
| Cross-machine | Peer daemons, no hub: each machine's daemon owns its agents and their mail. Requests about an agent elsewhere go to the daemon that owns it; agent lists and the human inbox merge across peers. Peers are listed in `settings.json` with their URL and token | Fits the single-machine code with few changes and has no single point of failure. A VPN such as Tailscale can connect the machines. Revised from a hub on 2026-10-10. |
| Agent-facing API | One MCP server, `stam mcp`, a thin stdio process that proxies to the local daemon | Works in every MCP harness. Logic lives in the daemon, so updating it rarely needs an MCP reconnect. |
| Text sent to agents | Every notice, instruction, and system message comes from an editable template file, never a string in code | The rule: all of it readable and modifiable in the UX. |

## Processes

```
  alpha                                       storage
  ┌──────────────────────────────────┐        ┌──────────────────────────┐
  │ stamd (systemd user service)     │◀──────▶│ stamd                    │
  │  registry + mail of its agents   │  HTTP  │  its own agents and mail │
  │  tmux -L stam: one session/agent │ Tailnet│  ...                     │
  │  adapters · web UI · terminals   │        └──────────────────────────┘
  └───▲───────────────▲──────────────┘
      │ stdin/stdout  │ hook commands
  stam mcp (per agent)   stam hook <harness>
```

- `stamd`: the daemon, one per machine, installed as a systemd user service with `stam daemon install`. It runs the deployed release (`STAM_HOME/releases/current`, built by `stam deploy`), not a checkout, and agents' MCP shim and hooks use that release's `bin/stam`. HTTP + WebSocket on `127.0.0.1` and the Tailscale address, port 7878 by default. Peers are listed in `settings.json`.
  - No network git (`ls-remote` or `fetch`) on a daemon request path: it blocks the event loop for the whole timeout. Use the local remote-tracking refs (S-1424).
- `stam`: the CLI. Every command is a call to the local daemon, so the CLI and the web UI share one API.
- `stam mcp`: per-agent stdio MCP server. Reads `STAM_URL`, `STAM_AGENT_ID`, and `STAM_TOKEN` from its environment. For Claude Code it also declares the `claude/channel` capability and turns daemon pushes into channel notifications.
- `stam hook <harness> <event>` and the status-line command `stam statusline <harness>`: they run on every tool call and every status-line refresh, so `bin/stam` sends them to a shell + curl path (`bin/stam-fast`) that never starts node, falling back to the CLI when curl, `timeout`, or a JSON parser is missing. Both read the harness's stdin JSON and POST it to the daemon; the hook prints the daemon's reply, such as a mail notice as `additionalContext`, and the status line prints its prefix and then the user's own status-line output. If the daemon is down a hook exits 0 silently, so a dead daemon never blocks an agent.

## Data model

- `machines`: id, name, url, last seen.
- `harnesses`: name, adapter, version, supported models, effort levels.
- `models`: id, provider, capabilities (image, video, and so on), prices per million tokens. Public prices by default, user-overridable.
- `presets`: named harness, model, and effort combinations, with a description of when to use each. Ships with defaults.
- `agents`: id, name (human-readable, unique), role description, machine, harness, model, effort, workspace spec, cwd, parent id, resume id, lifecycle, activity, activity detail, capabilities, context tokens, visibility rules, timestamps.
- `mail`, `mail_recipients` (read state per recipient), `attachments`, `lists` and `list_members` (broadcast).
- `events`: append-only log per agent: hook events, state changes, notices sent. Feeds the UI timeline and debugging.
- `itsas` (id, key, parent_id, kind, title, summary, body, status, owner, thread_id, created_by, created_at, updated_at, closed_at), `itsa_participants`, `itsa_links` (system, external_id, url), append-only `itsa_events` (status, owner, and other field changes), and `itsa_counter` (the durable key counter). Readable keys like `S-42` from `settings.itsa.keyPrefix`; statuses from `settings.itsa.statuses`, each in one of five fixed categories and flagged when it waits on the human. One nestable type: initiative, project, milestone, and issue are only a `kind` label. Owners and participants may be agents on another machine, resolved through peers. See `docs/itsa-design.md`.

Agent ids are short and global, minted by the hub, for example `a7k3f`. Names like `chief-of-staff` or `auth-worker` are unique aliases.

A model doesn't need to be in the registry to be used: spawn passes the model string straight to the harness, so a model released today works today. The registry only adds descriptions, capabilities, and prices.

## State

Two fields per agent:

- **Lifecycle**: `active`, `paused`, `shut_down`, `archived`.
- **Activity** (meaningful when active or paused): `working`, `waiting` (with what: tool, agent, human, job, timer), `blocked` (permission or elicitation), `errored` (with reason), `idle`, `unknown`.

The UI shows one combined state, matching the eight states in the idea doc. Sources per harness:

| Harness | Working | Blocked | Idle or finished | Errored | Context size |
| --- | --- | --- | --- | --- | --- |
| Claude Code | `UserPromptSubmit`, `PreToolUse` | `PermissionRequest`, `Notification` | `Stop`, `Notification idle_prompt` | `StopFailure` | statusline JSON |
| OpenCode | `session.execution.started` | `permission.asked`, `form.created` | `session.execution.succeeded` | `session.execution.failed` | last assistant message tokens |
| Codex | `thread/status/changed` active, `UserPromptSubmit`, `PreToolUse` | `waitingOnApproval`, `waitingOnUserInput` | `idle` (`Stop` hook as fallback) | `systemError`, `turn/completed` failed | `thread/tokenUsage/updated` (last call's input) |

Telling "waiting for the human" apart from "idle" and "waiting for a job" is partly a question the agent answers itself: the MCP has a `set_status` tool, and `Stop` with a running background job counts as waiting.

An agent whose turn has ended and that has at least one open wait is `waiting`. Waits live in the `waits` table: kind (open-ended: `children`, `human`, `agent`, `timer`, `job`, later more such as CI), target, short detail, since, optional until, source (`stam`, `hook`, `declared`), and JSON data. `db.syncWaits` sets the activity: a turn ending with waits, or a wait added to an idle agent, makes it `waiting`, with a detail naming the top wait (human > agent > children > job > timer) and a count; the last wait clearing makes it `idle`. Working, blocked, errored, and starting are never overridden. A waiting agent takes prompts and mail like an idle one. Every kind of wait holds back its parents' tree-idle notice, which fires once, when the last wait clears and the subtree is quiet. The agent JSON (`/api/agents`, `find_agents`) carries `waits`; `POST /api/agents/ID/waits` adds one and `…/waits/clear` clears by id or by kind and target. Mootr fills in two kinds from its own data (source `stam`): a `children` wait on an agent while any agent below it is busy, whose detail counts the busy descendants, recomputed for its ancestors whenever an activity changes, a permission opens or resolves, or an agent is spawned, archived, shut down, or reparented, and cleared when the subtree goes quiet; and one `human` wait per pending permission request (target the request id, detail "your approval"), cleared when the request is answered or withdrawn. A daemon start rebuilds both kinds for every agent, so a restart neither loses nor leaves stale waits.

Claude Code reports its own waits (source `hook`, `src/adapters/claude.ts`). Every `Stop` payload lists what is still open: `background_tasks` (Bash or Monitor with `run_in_background`, background Agents) become `job` waits and `session_crons` (CronCreate, and ScheduleWakeup, stored as a one-shot cron) become `timer` waits, targets being the task and cron ids; each `Stop` replaces the hook waits with those lists. A turn started by a task notification or a one-shot timer's prompt clears that wait at `UserPromptSubmit`. Jobs and crons survive `/clear`; `SessionStart` on `startup` or `resume` drops the hook waits.

Codex and OpenCode report theirs as `job` waits too; neither has timers. Codex (`src/adapters/codex.ts`): the agent's thread's `commandExecution` items still in progress (background terminals) and `subAgentActivity` sub-agents not yet `completed` when the turn ends; each clears on its own end event, and Codex doesn't wake the agent for it. After every turn and on (re)subscribing, the list is checked against `thread/backgroundTerminals/list` and the active child threads; a launch drops the hook waits. OpenCode (`src/adapters/opencode.ts`): the session's running `shell.created` shells and running child sessions (`parentID`) when its execution ends; OpenCode starts an execution with a completion notice when one ends, which drops its wait (or 30 seconds without one). Each connection to the server reads the running shells and child sessions again, which drops waits for work a restarted server lost.

An agent declares its own wait for a reply with `wait_for`: kind `agent` (mail from that agent to it, in a named thread if one is given) or `human` (mail from the user), source `declared`, optionally with `timeout_minutes`. The awaited mail clears it; the timeout clears it and sends the agent a notice. `wait_done` clears one of the agent's own declared or timer waits. `wake_me` schedules a timer (kind `timer`, source `stam`, `data` holding the schedule): one-off (`in_minutes` or `at`) clears when it fires; `cron` (a small 5-field parser in `src/waits.ts`) and `every_minutes` move `until` to their next fire time and stay until `wait_done`; when one fires, the agent gets its note as a notice. One scheduler in the daemon (`waits.startScheduler`, driven by `until`) runs timeouts and timers; its first tick at start catches up on what came due while it was down, once, never per missed tick. Declaring a wait on another agent sends that agent one notice naming the thread. Only the agent itself, one of its parents, or the human may create or clear its waits, and mail mootr sends on its own behalf never clears a declared wait.

## Harness adapters

Each adapter implements the same small interface:

| Operation | Claude Code | OpenCode 2 | Codex |
| --- | --- | --- | --- |
| launch | `claude --session-id ID --settings FILE --mcp-config FILE --append-system-prompt-file FILE --dangerously-load-development-channels server:stam`, with generated files under the agent's state folder, so the workspace isn't touched | TUI attached to the shared server: `opencode --server URL --session ID`, plugin through config (it fetches the system prompt from the daemon) | per agent, `codex app-server --listen unix://SOCK` with `-c` overrides (hooks, MCP, permissions); the daemon opens the thread with `thread/start` (system prompt as `developerInstructions`) and `thread/name/set` (which writes it to disk), then `codex resume THREAD --remote unix://SOCK` in the same tmux session; the user's `~/.codex/config.toml` isn't touched |
| first prompt | typed into the input box once it's up: one bracketed paste through tmux's stdin, then Enter (counts as the user's own message, as auto mode needs) | `POST /api/session/{id}/prompt` | app-server `turn/start` once the TUI is up |
| notice during a turn | `PostToolUse` hook `additionalContext` | plugin `tool.execute.after` | `PostToolUse` hook `additionalContext` |
| prompt to idle agent | channel push (fallback: the session's inbox socket) | `POST /api/session/{id}/prompt`, `delivery: queue` | app-server `turn/start` |
| compact with instructions | when idle: quit, `claude -p --resume ID "/compact …"`, relaunch with resume | `POST …/compact` plus plugin hook | `thread/compact/start` |
| resume | `claude --resume ID`, note as the first prompt | `--session ID`, note as the first prompt | `thread/resume` with `developerInstructions`, then `codex resume ID --remote unix://SOCK`, note as the first prompt |
| MCP reconnect | restart flow (quit and resume) | `POST /api/experimental/mcp/{name}/connect` | `config/mcpServer/reload` |

No prompt, note, or system prompt ever goes on a command line: every process on the machine sees command lines (`ps`), and a broad `pkill -f PATTERN` matches them. An agent once killed another agent's Claude Code with `pkill -f` because that agent's first prompt named the path it matched. Launch commands carry only paths, ids, and settings; the text goes in after launch through each harness's own channel (row "first prompt"), and Claude Code's headless `/compact` reads its command from stdin. The system prompt also tells agents never to kill by a broad pattern and to touch only processes and test folders they created.

A `generic` adapter runs any other harness in tmux with state `unknown` and terminal-only input, so every harness works from day one at a lower level of control.

Claude Code launch dialogs (folder trust, new MCP server, development-channel warning) are answered by the node daemon right after spawn, before any human attaches, and the first prompt is then typed in. These are the only keystroke injections in the design, besides typing the human's approval (Permissions).

## Mail

- A mail has sender, recipients (agents or lists), subject, body, attachments, and a thread. Threads work like Slack threads: `send_mail` with `reply_to` puts the reply in that mail's thread (the subject defaults to the thread's). An agent's mail without `reply_to` still lands in a thread when it answers one, because models forget the parameter: a mail from a recipient that the agent read in the last 30 minutes and hasn't answered; else, for an empty or "Re:" subject or one matching a thread's, the latest such thread with a recipient in the last week. `new_thread: true` opts out; the tool result says when a mail was threaded this way. Across machines the sender's daemon resolves the thread and forwards its id. Mail from before threads was grouped once by "Re:" subjects. `read_thread` gives an agent the thread's messages it sent or received.
- Mail to the human: the system prompt carries the mail-to-human template (standalone, short, outcome first, one issue per thread, each reply restating where the issue stands) and one of `human-mail-when-necessary|important|everything.md`, picked by `settings.humanMail.when` (default `necessary`). Mail between agents has no such rules. Running agents get a changed rule at their next restart.
- The body is capped at about 5,000 tokens (config); overflow becomes an attachment automatically.
- Attachments are stored on the hub and fetched over HTTP, so mail works across machines.
- Delivery when a mail arrives, by recipient state:
  - **working**: every `PostToolUse` while unread mail exists returns the notice template: strict instructions to stop if possible and read the inbox, plus the subjects of the latest 10 unread mails.
  - **idle or waiting for input**: the adapter pushes the same notice as a prompt. Mails arriving within 2 seconds are batched into one push.
  - **blocked**: held until it unblocks.
  - **paused**: delivered like idle; a paused agent can still read.
  - **shut down or archived**: held; a config flag can wake the agent instead.
- **ITSA mail** (`docs/itsa-design.md`): a comment or update in an ITSA's thread is mail with `itsa_id`, `kind` (`comment` or `update`), and for updates a `health`. The ITSA's first post creates the thread (subject `KEY Title`, stored in `itsas.thread_id`). Posts run on the ITSA's home daemon, which sends to the participants minus the sender plus any `to`, and makes the sender a participant; `send_mail` with `reply_to` into such a thread is the same post. These copies are *quiet*: a working agent's `PostToolUse` notice leaves them out, and they arrive with the idle batch. They interrupt like other mail when the body names the recipient as `@name`, the sender is the human, or the sender is the ITSA's owner; the home daemon decides and sends the list of interrupted recipients along, also to other machines. `GET /api/itsas/ID/thread` merges the thread's mails (from every daemon holding a part) with the ITSA's status and owner changes as one-line events, by time; the events are not mail. **Waiting on the human (step 8, `src/itsa-human.ts`):** when an agent moves an ITSA into a status flagged `human`, the home daemon adds the human as a participant and posts one mail to the human only, kind `ask`, from the agent that made the change (else the owner, else the agent standing in for mootr), rendered from `templates/itsa-human.md` with what the status asks and the owner's latest comment or update. Setting the same status again sends nothing; moving to a different human status sends again; the human's own change sends nothing. `settings.itsa.actions` maps a status to its actions (`id`, `label`, target `to`, and `text`: `none`, `optional`, or `required`); the defaults are Approve (`needs_review` to `ready_to_merge`, `needs_approval` to `in_progress`, `needs_test` to `done`; `ready_to_merge` isn't a human status by default, since a manager merges, so the move doesn't notify the human), Request changes (to `in_progress`, text required), and Answer for `needs_input` (to `in_progress`, text required). `GET /api/itsas/ID` carries the current `actions`; `GET /api/itsas/attention` lists every ITSA in a human status with `since` (when it entered), `actions`, and `ask_thread_id` and `ask_mail_id` (its latest `ask` mail to the human, which always sits in the ITSA's own thread; null if none), oldest first; `POST /api/itsas/ID/act` `{action, text}` (the human only) moves the status only if the ITSA is still in the status the action was offered for (else `409`, `status changed: …`), then posts the text as the human's comment, which interrupts the owner. The human's own move sends no mail, also into another human status. Creating an ITSA straight into a human status mails like a move into it.
- Tree visibility rules (outside the tree, siblings, registry awareness) are enforced by the hub on `send_mail` and `find_agents`.

## Event subscriptions

Sources such as GitHub, Linear, and Slack hand the daemon normalized events through `POST /api/events`: source (for example `github`), type (for example `pull_request.synchronize`), subjects (the keys the event is about), actor, url, one-line summary, JSON payload, and a `dedupe_key`; a repeat of the same key is dropped. The daemon stores them in `ext_events` and matches every unexpired subscription in `event_subscriptions`, then delivers. `GET /api/events?subject=` reads them back.

A subject key names what an event concerns: `github:OWNER/REPO#N` (a pull request or issue), `github:OWNER/REPO` (a repository), `linear:TEAM-123` (an issue), `linear:team:KEY` (a team), `slack:CHANNEL` (a channel). A subscription's filter holds `source`, `subjects`, `types`, `actors`, and `exclude_actors`; the subject and type entries are glob patterns where `*` matches within one segment (up to the next `/`), so `github:example/*` is broad and `github:example/stam#12` is exact.

A subscription names a subscriber: an agent (delivered as an in-turn notice while it works, or mail from mootr when it is idle, routed to a peer when it is on another machine), an ITSA (a quiet post into its thread, as mootr), or the human (mail, one thread per subscription). Events for one subscription within 20 s fold into one delivery listing each summary and its url. An agent may subscribe itself, an agent in its tree, or an ITSA it owns or takes part in; the human anything. Agents create and manage them with the `subscribe`, `unsubscribe`, and `list_subscriptions` MCP tools (CLI `stam subscribe|unsubscribe|subscriptions`, API `GET|POST|DELETE /api/subscriptions`). Expired subscriptions are deleted as events arrive. A subscription's filter may also carry `ends_on` (event types): once one of those is delivered the subscription is deleted, so `watch_pr` (S-446, `src/mcp.ts`; `unwatch_pr` removes one) watches one PR and ends at its merge or close. Sources (pollers) are later changes; the `subscriptions` cost table is unrelated.

An agent may also declare an event wait: `wait_for on='event'` with a filter (source, subject and type globs, actors) and an optional `timeout_minutes`. It shows the agent as waiting like any declared wait, and clears on the first event a source posts that fits it, leaving that event's summary and url as a notice (a prompt if the agent is idle). An ITSA whose link URL names a subject — a GitHub pull request or issue (`github:OWNER/REPO#N`), or a Linear issue (`linear:TEAM-123`), from `subjectsForUrl` — is subscribed to that subject by mootr for as long as the ITSA is open; removing the link or closing the ITSA deletes the subscription and reopening recreates it, one per ITSA and subject. `watchedSubjects()` lists the distinct subjects of live subscriptions and open event waits, which the pollers (S-55, S-56) watch.

Voice input (`src/voice.ts`, S-72) is one human-only route pair: `POST /api/voice/transcribe` takes one recorded clip as its raw body and returns `{text}` from ElevenLabs Scribe; `GET /api/voice` returns `{configured}` (true or false only). The key lives in `STAM_HOME/voice.env` and never leaves the daemon. The clip is held in memory and never stored. Spend is recorded under the `elevenlabs` account, purpose `voice:transcribe`.

The GitHub source (`src/sources/github.ts`, S-55) is the first poller: the daemon starts it, and every `settings.watch.githubSeconds` (default 60; 0 disables it) it polls each watched subject that names a repository (`github:OWNER/REPO`) or a pull request or issue (`github:OWNER/REPO#N`); a glob subject is skipped. The `gh` login's token (or `STAM_GITHUB_TOKEN`, with `STAM_GITHUB_API`, for tests) authorizes the calls. It keeps one snapshot per subject in `watch_state`, sends `If-None-Match` with each request's stored ETag so an unchanged response is a 304, and backs off when `x-ratelimit-remaining` drops below 200 until the reset. The first poll of a subject records its snapshot without emitting; each later change becomes one event with a stable dedupe key: a pull request opening, closing, merging, reopening, becoming ready or a draft, a new head (`pull_request.synchronize`), its checks finishing (`checks.completed`, naming the ones that failed), a review, a comment, and issue changes; a repository's own events map their type (a push names its branch and count). `GET /api/watch/state?subject=…` (repeatable) returns what the poller last saw per subject for the dashboard (S-65).

The Linear source (`src/sources/linear.ts`, S-56) polls the same way, through Linear's MCP server rather than an API key: the `linear` entry in `mcpServers`, logged in once through the shared OAuth (S-50). Every `settings.watch.linearSeconds` (default 60; 0 off) it calls the server's `get_issue` and `list_comments` tools (names in `settings.watch.linearTools`) through `src/sources/mcp-client.ts`, a small streamable-HTTP client whose bearer comes from the daemon's login store and whose one 401 asks for a refreshed token. It keeps a snapshot per `linear:TEAM-123` subject in `watch_state` and emits one event per change: `issue.state_changed`, `issue.assigned`, `issue.priority_changed`, `issue.title_changed`, and `comment.created`, each with a dedupe key that names the change's time (or the comment's id). The first poll is silent. A `linear:team:KEY` subject polls the team's issues: `settings.watch.linearTools.teamIssues` (`list_issues`) lists every page of those changed since the team's cursor, sorted locally, so the order Linear lists them in does not matter. A list that does not move on (its `endCursor` is the one it was asked for) or runs past 200 pages fails the poll, and the cursor stays put. The first poll sets the cursor and the baseline to now and reads no history. The poll processes them oldest first, and at most 10 issues' comments (`list_comments`) a tick; the rest carry over. Each issue keeps its snapshot under `linear:team:KEY/ID` in `watch_state`. The cursor (the newest change processed) and the baseline (the team's first poll) are in the team's row, so a restart resumes there. A team's events carry the team alone as their subject, name the issue in `payload.issue`, and dedupe under the team's own keys, so an issue-only subscriber hears a change once. An issue first seen after the baseline emits `issue.created`; one created before it but changed since emits `issue.updated`. An issue already snapshotted at its `updatedAt` is passed over without a comment call, so a bulk edit cannot hold the cursor. A 429 pauses every team's poll for five minutes; a tick that outlives its interval makes the next one join it (`tickOnce`), not stack, and dropping the last subscription on a team deletes its rows. Linear may not bump `updatedAt` for comment-only activity, so a comment alone may go unseen; that is unverified until someone logs in. With no login or no `linear` server, the tick logs once and skips. The real tool names and result shapes are unverified until someone logs in; the parsing is defensive. `GET /api/watch/state` reports a Linear subject's state, assignee, priority, title, and url.

## MCP tools

- Registry: `whoami`, `register`, `find_agents`, `registry_info`, `usage_info`.
- Mail: `send_mail`, `list_inbox`, `read_mail`, `read_thread`, `itsa_post` (comment or update into an ITSA's thread; CLI `stam itsa post`, `stam itsa thread`).
- Agents: `spawn_agent` (the new agent is the caller's child), `agent_control` (pause, unpause, shutdown, archive, resume, restart, reconnect-mcp, adopt, set-visibility), `compact_self`, `reconnect_mcp`.
- Permissions: `request_permission`, `answer_permission`, `suggest_input` (Claude Code only: one exact line the human approves and mootr types into the agent's own input, S-422).
- Rings: `ring_create`, `ring_submit`, `ring_decide`.
- Events: `subscribe`, `unsubscribe`, `list_subscriptions` (Event subscriptions below; CLI `stam subscribe|unsubscribe|subscriptions`).
- ITSAs: `itsa_create`, `itsa_get`, `itsa_list`, `itsa_set`, calling the API as the calling agent; every agent's system prompt gets the `itsa.md` template. (`itsa_post` comes with threads, step 3.) **Owners (step 4):** `spawn_agent itsa=ID|KEY` (also `stam spawn --itsa`, and `itsa` in `POST /api/agents`) makes the new agent the ITSA's owner and puts the itsa-owner template block (key, title, summary, body, parent chain, links) in its first prompt, or makes it the whole prompt. The system prompt names the open ITSAs an agent owns, built on each start and resume. The parent ITSA's owner gets a queued notice (the channel child-turn notices use) when a child ITSA becomes `blocked`, human-flagged, or closed, and when a child's owner is shut down or errors; `settings.itsa.ownerNotices` (`on`/`off`) switches it. Archiving or forgetting an owner unowns its ITSAs, returns active ones to `ready` (in `itsa_events`), and tells the parent owner once (`src/itsa-owners.ts`).

## Permissions

Agents start in auto mode; only the human picks bypass permissions, in the web UI. An agent blocked by its harness's checks, or unsure an action is approved, uses `request_permission`: the human gets a mail with Approve and Deny on it, and the agent's parents and the chief of staff can review. The answer reaches the agent as a notice naming who answered. A harness dialog in the agent's terminal ("Claude Code asks to allow Bash") goes to the agent's parent and the chief of staff first (S-520): they deny it, with a note on what the agent does instead, or escalate it to the human with a one-line reason when the agent needs it and only a yes unblocks it. Only the human approves a dialog, since a typed Yes is the user's consent in the harness; with no live parent or chief of staff the dialog goes straight to the human. A paused parent or chief of staff isn't live, so an ask skips it for the next in line, then the human (S-589). A dialog none of them answers within `settings.dialogEscalateMinutes` (default 10) goes to the human as the same mail, naming who it was sent to; an escalation or answer first means it never does, and a dialog whose agent was shut down or archived is withdrawn instead. Settings changes are always the human's. The chief of staff and the assistant change the settings the same way (S-362): their write is a request showing a diff, applied only on the human's approval and only if the file is unchanged since the ask. A request and the asks its agent adds about it are one item (S-609): a `wait_for` human made while a request is pending with the human ties to it (the one its note names, the one whose thread it waits in, or, with no thread, the newest), and a decision mail naming it shows as the request's row; both settle when the request is answered, denied, withdrawn or expires, and the daemon settles any left from before on start. The web UI and the CLI outside an agent mark requests as the human's; agents run as the same Unix user and could forge that, so real isolation needs a separate user.

## Org structures

- **Tree or DAG:** `spawn_agent` makes the caller the parent; the chief of staff can adopt agents as co-parent. Parents hear when a child finishes a turn, gets blocked, or errors.
- **Visibility:** a parent limits a child's reach (everyone, its tree, or its parents) and registry view. The human, its parents, and the chief of staff stay reachable.
- **Chief of staff:** optional, named in settings. Every agent learns who it is; agents without a parent report trouble to it, or else to the human.
- **Rings:** members work on one topic in rounds, one at a time (fire), or as a debate, with an optional moderator who facilitates or decides. Ring turns arrive as fresh prompts.

## Usage and instructions

- **Usage:** spend and tokens per agent and day, from what each harness reports; Claude's 5-hour and weekly windows; mail to the human at thresholds in `settings.cost`.
- **Instructions:** each agent's system prompt lists the instruction files its harness skips (`CLAUDE.md` for OpenCode and Codex, `AGENTS.md` for Claude Code, subfolder files) plus `instructions.md` for all agents. Skills from `~/.claude/skills` and `STAM_HOME/skills`, and `settings.mcpServers`, reach every harness.

## Lifecycle flows

- **Pause**: send the pause template (stop running programs, prepare to resume later), mark `paused`.
- **Shut down**: wait for idle, quit the harness, store the resume id.
- **Archive**: ask the agent for its final round (`shutdown-prepare` plus the retro round of `shutdown-archive`), wait for its next turn end at most `settings.archive.finalRoundMinutes` (default 3), then shut down, run the workspace's cleanup (for example `git worktree remove`), and mark `archived`. On an agent whose harness is gone, a forced archive skips the turn-alive check and runs at once; force does not skip the final round's wait, which the deadline bounds. `discard` throws away uncommitted worktree changes; `force` implies `discard`, and neither skips the final round. An archive also refuses (S-2201) while the agent's branch has commits that no remote-tracking ref reaches (`git rev-list BRANCH --not --remotes`; a branch pushed to origin or storage counts as pushed), because removing the worktree would leave that work only under a local branch name: a repo with no remote passes (nothing to push to). The check runs first in `archive`, before the final round is asked for or anything is stopped, so the caller hears the refusal at once and the agent keeps running; `archiveLocked` repeats it before stopping the harness, and `cleanupWorkspace` once more before removing the worktree. The error names the branch, the count and the head, and says to push or `pr_open` first. `force_unpushed` (`stam archive --force-unpushed`) overrides it, and neither `discard` nor `force` does. A failed git check refuses. A pending archive that hits it at a turn end, on a dead harness or at its deadline clears, records `archive:failed`, and tells the parent (else the chief of staff); a cascade keeps a child that fails it. An agent already stopped or paused, or one whose harness is gone, archives at once. A wrap-up pushed while the agent ran a step may be held by the harness for the turn after (OpenCode queues it), so the step's end gives one more turn, bounded by a fresh deadline (S-1618); a plain shutdown works the same. A stop that leaves without a round records `archive:round-skipped` with `turn_ended_no_round` or `deadline_no_round`, and the later archive keeps that reason.
- **Respawn**: launch with the resume id, then the respawn template as the first prompt; from archived, the template says the workspace was removed.
- **Harness gone**: every 5 seconds the daemon checks each active agent's tmux session. One harness exiting while the tmux server lives marks that agent shut down ("harness exited"). When the whole tmux server went down (no server at daemon start, or a different server pid and start time than last check: a reboot or a crash), each active agent is marked shut down with a pending `recover` action and resumed with its conversation, one launch every 3 seconds, once one of the harness APIs answers (up to 10 minutes, for a daemon that starts at boot before the network). The note, `respawn-reboot.md`, says the machine restarted or the tmux server stopped and that its running processes were killed. A pending `recover` survives a daemon restart. Paused agents stay paused, and unpausing resumes them; agents without a session id stay shut down with the reason in their detail. Codex's TUI outlives a tmux crash with its app-server, so a Codex launch first stops any process naming the agent's socket. The OpenCode server, also in tmux, restarts on the next launch or event-stream reconnect, one start at a time.
- **Harness upgrade**: upgrade in the background, send the prepare-to-restart template, wait for idle, quit, relaunch with resume, send the upgraded template.
- **Context**: on each context-size update, compare against the agent's thresholds (warning, instruction, enforcement) and send the matching template. A size of 0 (a harness before its first model call) is no measurement. After a compaction, the first real size is the agent's base, and a threshold counts only once the size reaches base plus `idleCompaction.growthTokens`, so an agent whose summary alone is above a threshold isn't compacted again on every turn. Enforcement and the cache-aware idle compaction (idle 55 minutes and over threshold) use the adapter's compact operation, then send the post-compaction template.

## Workspaces

The spawn request names one of: an existing directory, a git worktree (created and owned by the agent, removed on archive), a script that prints a directory, or free-text instructions that the new agent follows to build its own workspace.

Separate from that working directory, a spawn may take a **personal workspace** (S-894): `workspace: true` makes a folder at `STAM_HOME/workspaces/NAME` (NAME the agent's own name) mode 0700, and a string names an existing or new one, so a respawned specialist adopts the folder of an archived one. It is never a git repo or worktree, and archive never removes it. `standing: true` marks the agent a long-lived specialist; for now it is stored and returned, and a later release pauses a standing agent with no work instead of archiving it.

A specialist shares its workspace with `workspace_share AGENT read|write|none` (S-896): the grantee sees the path in its workspace block, gets it as an allowed directory (Claude Code) or writable root (Codex, `write` only), and a notice. `read` is advisory, since every agent runs as the same Unix user. Grants belong to the folder, so a respawn that adopts an archived owner's folder inherits them; its block lists who the folder is shared with. A Claude Code grantee can use the path after its next launch (its notice says so); an agent's own workspace is in its allowed directories (Claude) and writable roots (Codex) from the start.

The phone and the desktop are designed with equal weight (a requirement): every view and interaction works by touch at 360-430 px as well as with a mouse and keyboard.

It uses React, Vite, strict TypeScript, lucide-react, and vitest. The shell uses worlds, Lucide icons, and a design system, kept in `docs/design-system.md` and binding here. A waiting agent's ring is dotted. The user adds tabs and splits there (a plain terminal in the agent's folder, other agents beside it, all its children, its inbox, config, usage), and each world keeps them. Later: artifacts, spaces, web page previews. Tabs drag between panes; agents drag in from the tree.

In the web UI that mail carries Approve (types "I authorize <id>: the user approved it (<action>)…" in one click, S-640) and Deny, or the answer once given; pending requests sit at the top of the mail list, and an agent's shield in the tree opens its request. A thread opens as its own world in main, in place of an agent's world: the thread, with a prompt input at the bottom to reply. A row that waits on the human, or holds one folded inside, shows a warning mark; the header counts them. **+** adds a root ITSA by title. The list polls `GET /api/itsas` every 4 s.

Each meter carries its initial and a level colour — neutral, warning over 80%, error over 95% (the status tokens) — so colour is never the only signal. Hovering a line on a desktop, or tapping it on a phone, opens a popover with the percentages, the used and total GB, the load average, and each core's CPU. The list polls `GET /api/machines` every 5 s (`src/machines.ts`).
- **Attention list:** the top of the mail list (the Mail tab on a phone) pins what waits on the human, oldest first: pending permission requests and every ITSA in a human status (`GET /api/itsas/attention`, polled every 4 s with the ITSAs). Each thing shows once: an ITSA whose ask thread is in the inbox is that thread's row, marked with its status glyph and label, and opens the ITSA (or the ask thread when the ask sits outside the ITSA's thread); an ITSA with no ask thread keeps a row of its own that opens its world; a request opens its thread. Like a pending request's thread, an ITSA's ask thread can't be archived while it waits (the server keeps it in the inbox). One count, `useWaiting` (`web/src/itsa/WaitingList.tsx`), is every `N waiting on you`: the Mail and Issues headers and the phone's Mail, Issues and Work badges. A click only stages the action (the staged-answer flow of decisions and permissions); the reply box's Send applies it with the typed text, and a `required` action keeps Send disabled until there is text. **Agent tree:** a row shows a chip with the key of the open ITSA it owns, or a count when it owns several, in the status tone (warning when it waits on the human); a click opens the ITSA, or a menu of them. Harness dialogs still with an agent's parent or the chief of staff show under the pinned rows in a collapsed group of their own, "With parent or chief of staff", off the count: read-only, each says what the agent wants (its dialog mail's subject) and who it is with, and opens the agent (S-594).

A row says who waits and why, and opens that ITSA, the request's thread, or the agent. `useWaiting` in `web/src/itsa/WaitingList.tsx` is the one definition, built from `store.attention`, `perms`, and each agent's `waits`; no endpoint.

A status's glyph shape is its category (dashed ring backlog, ring ready, half active, three quarters review, tick or cross closed), its colour the category's tone (`--is-*` in `tokens-stam.css`): blocked and statuses that wait on the human take warning.

One column per category, or (toggle) one per status, where an empty status column narrows to its name. Scope: direct children (roots), or the whole subtree flattened, where each card names its parent's key. It writes to the focused pane in main: an agent gets the text pasted into its terminal as typed input (`POST /api/agents/ID/prompt`, one bracketed paste, then Enter), a plain terminal gets it as a command line (`POST /api/shells/ID/input`). It acts for the human on every agent, by design (2026-10-11): it spawns under any parent or none, names the chief of staff, controls agents outside its tree, renames, reparents, kills, and forgets them (`set-parent`, `rename`, `chief-of-staff`, `kill`, `forget`, which other agents can't use), and answers any permission request. The agent takes half, its children share the other half, and each nesting level alternates between side by side and stacked. While it's on, the layout follows the agent tree as agents start and stop. - **Plain terminals:** `POST /api/shells` starts a login shell in tmux (`sh-XXXXX`, on the agent's machine), and the web UI attaches like an agent's terminal. Closing the tab ends the shell.

- **Phone** (up to 760 px wide; `src/ui/phone.ts` and the phone block in `style.css`): one world at a time and a bottom navigation: Agents (the tree over main), Mail (the mail list over main), Issues (the ITSAs over main, badged with how many wait on the human), the world in main (named for what it shows), and the assistant (full screen). The tree and the list cover main without changing it, so main comes back where it was. Main shows its focused pane with a strip of every tab in the world, a menu button (the agent's actions, the pane's, mootr's), and for a terminal a keyboard button. The prompt input's buttons keep the focus in its text, so a tap on attach or send doesn't drop the keyboard and move the button. Views don't take the focus by themselves on a phone, since focus raises the keyboard; staging an answer doesn't either.
  - **Terminals:** a vertical drag scrolls as the wheel does (tmux and the harness get wheel input); a tap doesn't raise the keyboard. The keyboard button does, and a row of the keys a phone keyboard lacks (Esc, Tab, Shift+Tab, arrows, Ctrl+C, Enter, and putting the keyboard away) replaces the prompt input while the terminal has it.
  - **Touch:** every target is at least `--size-hit-touch` (44 px), inputs are 16 px so iOS doesn't zoom, and what hover shows on a desktop shows at rest (a tree row's menu button, the active tab's close button, a file's remove button). A long press opens the context menu (Android sends one; `phone.ts` sends one on iOS). Menus open as a sheet at the bottom. A rank row's number is a grip that drags it by touch; its arrows work too.
  - **Safe areas:** the shell, the navigation, and menus pad by `env(safe-area-inset-*)`.

## How we build it

Lessons taken from the earlier proof of concept (`stam`) as risks to guard against, not proven causes: each milestone is tested end to end against a live cheap agent (`claude-haiku-5-5`, DeepSeek flash in OpenCode); a detector ships together with its consumer; the codebase and its docs stay small.

1. **Spawn and see**: daemon, SQLite registry, tmux spawn of Claude Code with hooks, live state, `stam spawn`, `stam ls`, `stam attach`.
2. **Mail**: `stam mcp` with mail tools and the channel; notices during turns and pushes to idle agents; two agents mail each other.
3. **Web view**: agent list and live terminal in the browser, including from a phone.
4. **OpenCode adapter**: same tests as 1 and 2.
5. **Lifecycle and context**: pause, shut down, archive, respawn, thresholds, cache-aware compaction, harness upgrade, MCP reconnect.
6. **Cross-machine**: peer daemons, one per machine.
7. **Then**: permissions, org structures and rings, usage, instruction and skill sync, and the Codex adapter. All done as of 2026-10-10.

## Open questions

- Claude Code's auto mode runs a safety check on tool calls. It blocked an agent from mailing a "secret word" to another agent as possible data exfiltration. It was decided (2026-10-11) that mootr pre-approves its own MCP tools: Claude Code agents get `permissions.allow: ["mcp__stam"]` in the settings mootr generates, and Codex agents `default_tools_approval_mode = "approve"` on the mootr server.
- Claude Code opens menus over an idle agent's input, such as "Teach auto mode about your environment?". A menu captures keystrokes and can hold back pushed mail. mootr presses Escape on known menus over idle agents; the list is `banners` in `settings.json`. Unknown menus still need a human.
- Claude Code's startup banner says `server:stam · no MCP server configured with that name` for a channel given through `--mcp-config`, yet pushes through it work.

- Claude Code channels are a research preview behind a development flag; if they break, the inbox socket is the fallback, and its message format is undocumented.
- A live Claude Code session can't be compacted or have its MCP reconnected without typing; the design uses quit and resume instead, which costs a few seconds and drops the prompt cache.
- Codex delivery into an open TUI works (tested with 0.162.1): a turn that mootr starts with `turn/start` from its own app-server connection shows live in the `codex --remote` TUI, and a half-typed draft survives. Approval requests go to every client; mootr leaves them to the TUI.
- After `/clear` in a Codex TUI, the new thread is the TUI's own: mootr's system prompt reaches it as the `SessionStart` hook's added context (a later compaction may drop it), and its approvals reviewer is the TUI's default, because a TUI resuming a remote thread refuses permission overrides.
- Codex runs hooks only once their hash is trusted. mootr gets the hashes from Codex (`hooks/list` on a short-lived app-server) and passes them as `hooks.state` overrides, so it trusts only its own hooks and only in its own app-servers.
- Codex's sandbox needs unprivileged user namespaces. On Ubuntu with `kernel.apparmor_restrict_unprivileged_userns = 1` and no `bubblewrap` package, every sandboxed command fails (`bwrap: loopback: Failed RTM_NEWADDR`), so auto mode works only through escalations. Installing `bubblewrap` likely fixes it.
