# Go migration: catch-up list and Go-impact gate

Part of the Go daemon migration (S-2194). Two pieces track the TypeScript code that the Go port has not yet caught up with. The recurring finds from reviews of Go ports are in `docs/go-review-recipes.md`.

## Modules: `docs/migration/modules.json`

A JSON array with one entry per Go module that ports code from `src/`. It starts empty (`[]`). An entry has:

- `name`: the module's name, a lowercase word with dashes. A `Go-impact:` line names it (below).
- `globs`: the `src/` paths the module ports, as git pathspec globs (`**` crosses folders).
- `portSha`: the commit the module was last brought up to date with. Empty or absent means the module is not ported yet, and the catch-up list skips it.

Example entry (not in the file; add it to the array once the module exists):

```json
{
  "name": "mail",
  "globs": ["src/mail*.ts", "src/mail/**"],
  "portSha": "0123456789abcdef0123456789abcdef01234567"
}
```

## Catch-up list: `scripts/go-catchup.mjs`

```
git fetch origin
node scripts/go-catchup.mjs [MODULE]
```

For each module with a `portSha`, it prints the commits on `origin/main` since that SHA that touch its globs, newest first. Merge commits are left out, since the PR's own commits are listed. With `MODULE`, it lists only that module. Read-only: it changes nothing.

## Go-impact gate

A PR that changes `src/` must say which Go module it affects, or none, in a line of its body:

```
Go-impact: mail
Go-impact: none
```

The merge gate refuses a PR whose `src/` change has no such line, or a line that is neither a module name nor `none`. The check is off by default. It turns on with `STAM_GO_IMPACT=required` in the environment of the gate and the merge. It is planned to be turned on after phase 2 of the migration. Until then, a PR with no `Go-impact:` line merges as before.

The check reads only the PR body and the changed paths. It does not yet check that the name is in `modules.json`.

## Nightly parity run: `scripts/go-parity-nightly.mjs`

```
node scripts/go-parity-nightly.mjs --install   # once on storage, after the deploy that has the script
node scripts/go-parity-nightly.mjs --status    # the last run's summary line
```

A systemd user timer (`mootr-go-parity.timer`, or `stam-go-parity.timer` on a machine that hasn't moved to mootr; 03:30 host time, `Persistent=true`, so a missed night runs at the next boot) starts the matching `.service`, which runs the script from the deployed release (`~/.local/share/stam/releases/current`), so a deploy swaps the code and keeps the timer. `--install` writes both units to `~/.config/systemd/user` and enables the timer, under the `stam-` name under a real stam home (or while a `stam-go-parity` unit is installed) and the `mootr-` name under a mootr home, running `<home>/releases/current` (S-3349); rerun it after a change to the units. Storage only (the run refuses elsewhere).

A run:

1. Takes an exclusive lock (`go-parity/lock`) before anything else. A second run while one is going exits 75 with `another run holds the lock; refused`.
2. Fetches `origin/main` into its own clone (`go-parity/repo`, never `~/projects/stam2`), runs `npm ci` when `package-lock.json` changed, and builds `go/`.
3. Runs `scripts/go-parity.mjs` over the FREE list through `scripts/test-slot.sh` (one slot), with `STAM_DAEMON=go`. `test/lib.sh` creates each Go test home's `stam.db` with the TypeScript schema first (`test/go-seed-db.mjs`, which refuses the live home), because the Go daemon opens a database and doesn't create one.
4. Stops at `STAM_GO_PARITY_TIMEOUT_S` (default 4 h). However the run ends, `test/lib.sh` stops its daemons and tmux servers, a watchdog reaps a killed run, and the script then sweeps what is left by pid and removes its scratch folder. A stopped service takes its cgroup with it.
5. Publishes under `STAM_HOME/go-parity/`: `parity.json` (per-test results, the shape of `docs/migration/parity.json`, each test tagged `kind` and `daemon`), `parity.prev.json` (the night before), and `last-run.json` (state `ok`, `build-failed`, `install-failed`, `timeout` or `run-failed`; shas; counts; newly failing tests; the summary). It posts the one-line summary on S-2194 with `--system go-parity`: `Nightly Go parity (main 01234567): 7 of 9 daemon e2e tests pass (+2 since last night, 300 n/a); newly failing: x, y.` Only names, counts and shas are written; test output and the environment never are.

What counts (`scripts/go-parity.mjs`): a test's `kind` is `node` (a `node --test` file that runs in-process) or `e2e` (a shell script), and `daemon` is true when the script starts a daemon with `daemon_up` or `isolate`, so it can run against `go/bin/stamd` under `STAM_DAEMON=go`. Only those say anything about Go, so the headline is `E of N daemon e2e tests pass`; every other test is `n/a` (it passes or fails the same without Go). The UI flows (`ui*`, `daemon-stub`) start the TypeScript daemon through `web/check/daemon.sh` and are n/a too. A test that prints a line starting `SKIP` and exits 0 ran nothing; `test/run.sh` shows it as `SKIP` (the exit status is unchanged) and parity records `skip`, not `pass`. A failure whose output or kept log (`DIR/NAME.log`, the folder `test/run.sh` names) shows a full disk or quota (`ENOSPC`, `EDQUOT`, `No space left`, `Disk quota exceeded`) is run once more. The run ends with `parity: E of N daemon e2e tests pass, S skipped, M n/a`.

The committed `docs/migration/parity.json` is not touched; a module PR updates it from `parity.json`. Tested by `test/go-parity-nightly.test.mjs` (`go-parity-nightly-unit`, free).

## Deliberate differences from TS

Places where the Go daemon is meant to differ from the TypeScript one. A parity test that finds one of these is fixed, not the daemon.

- **The human's proof with `x-stam-local` and no token is never the human** (#1291, S-4100). On Go such a request is Kind owner but never `Owned`, so it can't mail as the human, approve suggested input or drop a draft. TS's test-key and tailscale-serve paths ignore the header and treat it as the human. This is fail-closed, and no real caller sends it: a peer always sends its token with `x-stam-local`, and a browser never sends the header. TS's local session (`localDirect`) and its strict `human` already refuse `x-stam-local`.
- **`stam ring` inside an agent names its creator** (#1293, S-4154). Both daemons' `POST /api/rings` take the creator only from `by` or a human caller. TS's CLI sends no `by`, so inside an agent its ring start is refused with "a ring needs a creator". Go's CLI sends the agent's id as `by`, which `resolveActors` checks against the token.
- **An MCP canary asks the daemon nothing** (#1294, S-4154). A canary is a release's MCP server started with `STAM_MCP_CANARY` to prove it answers a `tools/list`. Go's canary lists the `req_*` tools hidden instead of asking `GET /api/req-enabled`, so it calls the daemon for nothing (`TestAdoptedSession`). TS's canary asks. The canary's answer is only checked for listing tools.
- **The Needs you list projects a peer's rows** (#1300, S-4154). Go's `GET /api/asks` keeps only the Ask fields of each row a peer returns, and sets a permission row's `what` to its kind label, before it merges the rows. A peer can't put a request's text, or any other field, on the list, including when its settled copy replaces an open row here. A row of a kind the list doesn't know is dropped. TS passes the peers' rows through as they are.
- **A peer's MCP status and lease errors carry no text from the home** (#1384, S-4416). Go keeps a home's status row only when its name is one of this machine's configured servers, shows it under the local name, and shows its `type` only as `oauth` or `gh`; a home server this peer has no config for isn't listed. A lease error's cause is built locally: the home's known refusals are matched exactly by status and keep their words, the variable parts of the rest (numbers, machine names, provider text) are dropped, and unknown text gives no cause. The url-mismatch error names only this machine's url. TS spreads the home's row and echoes its error text and url (S-4498).
- **`ChosenOption` splits lines where JS's multiline `^`/`$` do** (#1300, S-4154). Go's regexp breaks lines only on `\n`, so Go matches `Chose **X**.` line by line, splitting on `\n`, `\r`, U+2028 and U+2029, and counts the 80-unit limit in UTF-16 units. A CRLF reply matches as in TS. An option that holds a lone `\r` records no label on Go, where TS's `[^*\n]` would take it.
- **A settings ask that no longer waits keeps no secret in its payload** (S-3869, S-4154). Once a settings ask is approved, denied or withdrawn, or its agent is forgotten, Go rewrites `permission_requests.payload` in the same transaction: secrets are replaced as an agent reads settings, a store name is kept, the hashes are dropped, and `"redacted": true` is added. A start redacts the payloads decided before. TS keeps the plaintext until the row is deleted. No route serves the payload on either daemon.
- **A layout op of the wrong shape is refused in Go's words** (S-4198). An op or pane tree that makes TS's `src/layout-ops.ts` throw a TypeError or SyntaxError (a `setRoot` with no root, a `current` whose world is neither a name nor null, a split whose children aren't a list) is a 400 on both daemons and changes nothing. TS's message is the engine's (`Cannot read properties of undefined ...`); Go's says `not a layout op this layout can take` with what was wrong. Every other refusal is TS's text, checked op by op by `go/internal/layout/testdata/layoutref.mjs`.
- **The web UI's files never come from outside `web/dist`** (#1309, S-4198). Go reads the page, the stories page, the service worker and every `/web/` asset through an `os.Root` on `web/dist`, so a symlink or `..` that leads out of it is refused: the page and the stories page answer 503 as unbuilt, the service worker and an asset 404. These routes answer before any auth. TS's `readFileSync` follows such a symlink. A symlink inside `web/dist`, and a symlinked path to it (a deploy's `current`), work on both.
- **A listing re-checks the folder it opened** (S-4198). `GET /api/files/list` opens the checked folder once, re-checks its real path through `/proc/self/fd`, and reads its entries through that handle. A folder on the way that was swapped for a link between the check and the open is refused with 403 `the folder moved` when the folder it now reaches is outside the roots or on the deny list. A swap to another allowed folder lists that folder, as TS does. TS lists whatever the link points to.
- **An archived agent's event subscriptions are dropped** (S-4317). TS leaves the subscriptions of an archived agent in `event_subscriptions`, inert; Go deletes them, with the delivery each has folded and the notices of the agent's cleared event waits, when the archive finishes (`ForgetAgentEvents`), so a daemon never keeps a timer or a queue for an agent that can't read it.
- **Folded event deliveries and cleared-wait notices live in `kv` rows** (S-4317). Go keeps a subscription's undelivered lines in `evq:<subscription id>` and the notice of an event wait an event cleared in `evw:<wait id>`, written in the ingest transaction, so a restart loses neither (TS holds them in memory and loses the batch). A delivery to a working agent stores its text as an `answer_notices` row in the same transaction that removes the lines (the lifecycle restores it after a restart and the agent's acknowledgement removes it); a delivery by mail removes the lines, and moves a human subscription's thread pointer, in the mail's own transaction. A notice the agent was handed but had not acknowledged when the daemon stopped reaches it once more. A remote ITSA post is a separate write, so a crash between the post and the removal posts again. A batch that keeps failing is kept and tried again after a longer wait (up to an hour), never dropped. A TS daemon after a rollback ignores `evq:*` and `evw:*`.
- **A GitHub poll that fails stores nothing** (S-4329). TS stores the snapshot of a poll whose answers were all errors as `{}`, so the next poll isn't the first and floods every old review and comment. Go fails the poll for any status other than 200 or 304 (a 404 on the issue view or on a head's check runs and status means absent, and is no failure), on any page of a repository's events too, and keeps the old snapshot, ETags and `since`. A rate limit (a 429, or a 403 with `x-ratelimit-remaining: 0` or `retry-after`) backs the whole poller off until the reset; any other failure, a permission 403 included, backs off only that subject for 5 minutes while the others go on (TS stops everything on any 403). An ETag that holds the token is dropped.
- **A GitHub poll's events and its snapshot are one transaction** (S-4329). TS stores the snapshot first, so a stop between the two loses the events. Go ingests the events and stores the snapshot in one write transaction, so a stop leaves both or neither; the check that the subject is watched is read in that transaction when it begins, so a merge that ends the watch still stores its final snapshot, and a subject unwatched before it stores nothing.
- **The poll state of a subject nobody watches is dropped after a week** (S-4329). TS never deletes `watch_state`. Go drops the rows of unwatched `github:` subjects at the end of a tick, in a transaction that reads the watchers itself, once the row was last written more than 7 days ago (a watch that comes back sooner reuses its baseline). It drops only issue, repository and legacy `{}` rows, never a pull request's, whatever its state: the diff header reads the review verdict of a PR whose watch ended.
- **A GitHub token's ETags are not reused by another token** (S-4329). TS keeps the stored ETags across restarts and token changes. Go keeps a hash of the token in memory only; after a start and after any token change each subject is polled once without `If-None-Match`, so one token's 304 is never taken for another's view. A 403 whose body names a rate limit (GitHub's secondary limit) backs every subject off, like a spent budget.
- **`watch_pr`'s default repository** (S-4329). Without `itsa.prOpen.github`, Go falls back to the origin of the `prOpen.repo` checkout, or of the only repo; TS takes the first repo's origin, and Go's repo map has no order, so with several repos and no `prOpen.repo` Go answers that no repository is known.
- **A Linear poll's events and its snapshot are one transaction** (S-4331). TS stores the snapshot, then ingests the events, so a stop between the two loses them. Go ingests the events and stores the snapshot in one write transaction (an issue's, or one issue of a team with the team's cursor stored after), so a stop leaves both or neither and the dedupe keys drop any repeat. The check that the subject is watched is read in that transaction when it begins: a subject unwatched before it stores nothing.
- **A rate limit pauses every Linear poll** (S-4331). TS pauses only the team polls for five minutes after an HTTP 429 and keeps polling issues. Go pauses all Linear polling, since the limit is on the login.
- **The poll state of a Linear subject nobody watches is dropped after a week** (S-4331). TS drops a team's cursor and snapshots at the start of the next tick and never an issue's row. Go drops the rows of every `linear:` subject (an issue's, or a team's cursor and the snapshots under it) once nobody has watched it for 7 days, at the end of a tick, in a transaction that reads the watchers itself; a watch that comes back sooner reuses its baseline.
- **No credential in a Linear error** (S-4331). Every error the MCP client returns, and every log line, is scrubbed of the bearer it used, including a server's reply that echoes the `Authorization` header; a transport error names neither the bearer nor the URL. TS passes the server's text through.
- **A second Linear tick is refused, not joined** (S-4331). TS `tickOnce` hands a caller the tick in flight; Go's `Tick` returns `ErrBusy`. Only the interval calls it, so the effect is the same.
- **A file the daemon can't open is a 500 in Go's words** (S-4198). `GET /api/files/read` on a file inside a root that the daemon may not open (no read permission, say) is a 500 on both daemons. TS's message is Node's (`EACCES: permission denied, open '...'`), Go's is `open ...: permission denied`. Every refusal (400, 403, 404, 416) is TS's text.
- **A review summary cut inside a character drops the half** (S-4198). `GET /api/diff`'s `review.summary` is cut at 200 UTF-16 units on both daemons. Where the cut splits a surrogate pair (an emoji, say), TS keeps the lone high surrogate, which `JSON.stringify` writes as `\ud83d`; Go drops it, since a Go string can't hold half a pair.
- **The diff serves only the PR's own files** (S-4198). `GET /api/diff/file` serves a path only when it has an entry in the PR's file list, and refuses with 403 an entry the deny list closes by its path or a rename's old path: `cert.txt` renamed from `secret.pem` holds the secret. A pinned `head` and `base` must be an exact pair this daemon listed for the PR, kept in memory with that list's deny outcome (the last 16 per PR), so no range a client picks can move the merge base under a denied file. Any other pair, and every pair after a restart, is a 404 that says to reload the diff. TS serves any path in the tree, and judges only the asked path. A PR with no merge base with main has no list, so its files are a 422 too, where TS serves the head side.
- **An origin URL with a credential in it isn't fetched** (S-4198). When a checkout's `remote.origin.url` carries a password (percent-encoded too), or any user on http(s) (where a token goes as the user), also inside git's `transport::address` form, `/api/diff` answers 500 before git starts, so the token is never on git's command line. TS fetches with it. Go also strips `user:token@` from any URL in a git error it passes on.
- **The diff cache's folders are named per repo and checkout** (S-4198). `STAM_HOME/cache/diff/NAME-HASH.git`, where HASH is 12 hex digits of SHA-256 over the repo's name and checkout, so `team/app` and `team_app` keep separate caches. TS names it `NAME.git`, so the two would share one. The cache is built in a temporary folder and renamed into place, and rebuilt only when git says it isn't a repo. Its recovery, build, fetch and pruning hold an flock on the sibling `NAME-HASH.git.lock`, so two daemons on one STAM_HOME never clean up under each other, and they free a killed fetch's ref locks. A timed-out fetch is killed with its whole process group, and that group is killed once git exits, so no child it left keeps running.
- **The agent view serves Claude Code and OpenCode** (S-4198, S-4237). Go serves `/api/agents/:id/view` and its `history`, `tools`, `prompt`, `interrupt` and `permission` routes for Claude Code and OpenCode agents. A Codex agent's view answers 409 `stam's own view doesn't support codex yet; use the terminal`, though the agent list's `view` still gives its capabilities as TS does, so the web offers the view and shows that error. TS streams Codex's from its server. An OpenCode agent's view reads the stored messages through the shared server's cursor and follows its event stream, as TS does; unlike TS, a prompt, a permission reply or an interrupt acts only on the session the agent runs when it is sent (it is refused with a 409 when the agent has moved to another session or is in a launch), and an open window whose agent moved to another session is emptied and read again from the new one.
- **A prompt from the view doesn't wake a resting agent** (S-4198). TS's `POST /view/prompt` to an agent resting under `standing-idle` wakes it with the prompt (S-2034); Go answers 409 `NAME is resting, and a prompt from the view doesn't wake it on this daemon yet; send it mail`, since the resting wake isn't ported. An empty prompt is still a 400 first.
- **An open view sees mail by polling** (S-4198). TS's view reads its mail again on `db.onAgentMail`; Go has no such hook, so each open view polls a mark of the agent's mail (its unread and read counts, and its sent mail's recipients and reads, with the newest read times) every 300 ms, the transcript follow's pace, and reads again when it moves. Only open views poll; the poll stops with the view.
- **Sending from the view never takes an agent's token as the human** (S-4198). `POST /view/prompt`, `/view/interrupt` and `/view/permission` need the human's own proof (`Owned`). TS's `humanOnly` takes the test human's header (`x-stam-test-human`, a test daemon only) whatever token comes with it, so an agent's token with that header is the human there; Go refuses it with the same 403.
- **A transcript row over 64 MiB is skipped** (S-4198). The agent view reads a Claude Code transcript row by row; a row longer than 64 MiB, finished or not, is dropped through its next newline. So one transcript's unfinished row holds at most 64 MiB, and each read scans only the new bytes. This bounds one row, not the view's memory: eight transcripts stay parsed, plus every one an open view follows, each with its parsed messages. TS keeps the whole unfinished row, and copies and rescans it on every read. Claude Code's rows run to a few MiB.
- **A prompt typed from the view that starts with `-` is text** (S-4198). Go types the human's view prompt with `tmux send-keys -l -- TEXT`; TS's `typeHumanInput` has no `--`, so tmux reads a prompt like `-n hi` as its own option and refuses it, and the prompt is lost.
- **Forwarded mail comes only from a peer, strict or not** (S-543, S-4100). `POST /api/mail` with `forwarded` or `relay` is refused with 403 `forwarded mail comes only from a peer` unless it carries the peer token with `x-stam-local`. Both skip checks the sender's own daemon made and may name any sender, the human included. TS takes them from the shared token too while `auth.humanStrict` is off, and only logs that strict would refuse them. `test/e2e-human-strict.sh` accepts either answer with strict off.
- **A peer UI's answer keeps `Vary: origin`** (S-4198). An answer to a peer's web UI carries `Vary: origin, accept-encoding`; TS's compressed answer replaces the `Vary: origin` it set with `accept-encoding`, so a cache could hand one peer's CORS answer to another origin.
- **The direct-refusal log line names Go's proof** (S-4198). A token-less browser write that is refused logs `direct request refused: METHOD PATH origin=ORIGIN: WHY`, as in TS, but with no host or origin check failing the reason is `not trustedHuman: the Go daemon proves the human by the test key or a local login only`. TS names the first failing tailscale check.
- **A fresh install's settings.json has no `itsa.repos`** (S-4198). On a first start both daemons write the defaults into `settings.json`, with `auth.localHuman` true. TS's defaults include `itsa.repos` with the repo derived from its own checkout, so TS writes that path into the file. Go's defaults have none, so the Go daemon's file leaves it out; Go adds the derived repo when it reads the settings, as it does for any file without it.
- **Local login ends the moment the setting is seen off** (S-4198). Go ends every local session, and any login still between its code check and its session's start, as soon as it sees `auth.localHuman` off: on a write through the daemon, or on its next read of a hand edit. TS ends them only when a later request checks the setting, so an off and on with no request in between keeps them, and a login checked before the setting went off still starts its session.
- **A local login's socket must match exactly** (S-4198). To find who owns the client's end of a connection, Go matches the whole reversed address and port pair in `/proc/net/tcp{,6}` (IPv4 connections on an IPv6 socket in their v4-mapped form), and finds no owner unless exactly one row matches. TS matches the two ports alone and takes the first row, so another user's socket with the same ports on other loopback addresses can stand in for the real one.
- **A local session counts only from the daemon's own Unix user** (S-4198). Go's `Direct` takes a loopback connection only when the client's socket belongs to the uid the daemon runs as, and never root. TS's `localDirect` takes any non-root uid, so another local user's browser with a stolen session token would pass.
- **A read that sees local login off ends the sessions before any later read returns** (S-4198). Go holds a reload lock from reading a changed settings file through its reload hooks, so a request that reads the setting on again (a quick off and on by hand) waits for the sessions to end first and is refused. TS has no such order.
- **An empty settings file keeps the last good settings** (S-4198). A settings.json that is there but empty, most often one caught mid-rewrite, is not valid JSON in Go as in TS; Go keeps the last good settings for it, so local login stays on and no session ends. TS reads its defaults then, apart from `cost`, which turns local login off and ends every session.
- **A local login's checks read the kernel's clock and only connected sockets** (S-4198). The daemon's start, which a code must postdate, is taken from a temp file's ctime, so a code made just after a start is never stamped before it (a ctime is coarse and can trail the wall clock by a tick; TS compares it with `Date.now()`). A socket's owner is read only from a connected row (state 01): Linux reuses a loopback tuple still in TIME_WAIT, whose row is root's, and TS's first-match would then find root.
- **The same user's processes can replay the browser's local session** (S-613; shared by TS and Go). A session token lives in the page's localStorage, so a process running as the human's Unix user (an agent among them) that reads it from the browser's profile passes as the human from this machine. Both daemons accept this residual; neither changes it.
- **A refusal names tailscale serve only on a test daemon** (S-4198). Go can't prove the human through tailscale serve yet (below), so `humanWays` names this machine's served page only where the test key stands in for serve's proof, and `stam web` doesn't list the serve hosts as needing no token. TS names both wherever a serve is found.
- **A launching queued spawn's name is taken** (S-4373). While a granted waiter of the developer slot queue launches, Go refuses a new spawn of its name (409 `name X is taken`) and a nameless spawn skips it; TS refuses only a waiting name, so a same-name spawn could race the launch's worktree.
- **A queued launch cut short by shutdown stays saved** (S-4373). Go leaves a granted waiter in `slot-queue.json` when the daemon stops mid-launch, so the next start queues it again unless its agent row exists; TS's file keeps it only when the process dies before its `finally`.

## Open gaps

Parts of TS the Go daemon hasn't ported yet. Each fails closed.

- **Tailscale serve's proof of the human** (S-4198). TS's `trustedHuman` asks `tailscale whois` who a request through `tailscale serve` comes from, and takes the tailnet owner as the human. Go has no such path: through serve only the test key (in a test home) proves the human, so elsewhere a served page is refused as not the human, and the human uses the local login on the machine itself.
- **Voice transcription** (S-4198). `POST /api/voice/transcribe` isn't ported, so `GET /api/voice` answers `configured: false` whatever `voice.env` holds, and the page offers no microphone.
